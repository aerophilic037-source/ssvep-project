현재 수집 실패의 단서가 이미 저장되어 있었다. **SSVEP 반응이 없다는 결론보다 먼저 전송 시간축과 큰 잡음 문제를 확인해야 한다.** 아래는 기존 파일의 관찰이며, 오늘 보드 상태를 직접 측정한 결과는 아니다.

원본은 수정하지 않았다. `~/Documents/OpenBCI_GUI/Recordings`의 OpenBCI RAW 21개와

저장된 브라우저 프레임 기록은 중앙값 약 59.88 fps, 최대 간격 약 17.7 ms다.
이 소프트웨어 기록만으로는 화면 쪽이 직접 거부 원인으로 보이지 않는다.

## 2. GUI 원본에도 낮은 행/시간 비율이 있다

| GUI RAW 파일 | 샘플 수 | 파일 내 시간 길이 | (N−1)/(마지막−처음) |
|---|---:|---:|---:|
| `2026-11-06_23-44-38` | 10,318 | 약 123.8 s | 83.34 Hz |
| `2026-11-08_22-11-34` | 146,408 | 약 1,850.8 s | 79.10 Hz |
| `2026-11-08_23-41-19` | 4,424 | 약 53.1 s | 83.35 Hz |
| `2026-11-08_23-45-02` | 6,894 | 약 82.6 s | 83.41 Hz |
| `2026-11-08_23-47-46` | 29,268 | 351.185 s | 83.34 Hz |

모두 헤더의 sample rate는 200 Hz다. 최근 세 파일에서 두 샘플이 같은 시각을 공유하고,
서로 다른 패킷 시각 사이 간격이 약 24 ms인 패턴이 보인다. 11월 8일 23:47 파일은 패킷 번호가
0–99 범위에서 같은 번호를 두 번씩 사용하는 형태다.

**이 관찰을 “ADC가 83 Hz로 동작한다” 또는 “58% 패킷 손실”이라고 단정하면 안 된다.**
보드 생성, BLE 전송, 드라이버 시간 부여, 버퍼 처리 중 어느 지점인지는 별도의 실시간 30초 계수와
직접 BrainFlow 비교가 필요하다. 중복 시각 자체는 BrainFlow 5.10.0의 Ganglion firmware 3
디코딩 코드가 두 샘플에 같은 `data.timestamp`를 쓰는 것과 일치한다.
[해당 버전 소스](https://github.com/brainflow-dev/brainflow/blob/5.10.0/src/board_controller/openbci/ganglion.cpp).

같은 세션의 `BrainFlow-RAW_2026-11-08_23-47-11_0.csv`도 대조했다.
29,268행, 시각 길이 351.185220초, 시각 기준 83.337790 Hz로 대응하는
`OpenBCI-RAW-2026-11-08_23-47-46.txt`와 같다. 각 행의 타임스탬프는 같고,
EXG 값의 최대 차이는 약 0.0000005 µV로 텍스트 소수점 반올림 수준이다.
따라서 이 사례의 낮은 행/시간 비율은 **BrainFlow 저장 데이터에도 존재하며,
OpenBCI 텍스트 변환이나 이후 LSL에만 생긴 현상이 아니다.**
이 비교는 GUI에 포함된 BrainFlow 출력끼리의 비교다. 별도 BrainFlow 프로그램으로
새로 수집한 하드웨어 비교 실험과 혼동하지 않는다.

## 3. 신호도 깨끗하다고 볼 근거가 부족하다

기존 NPZ 세 파일의 네 채널은 서로 매우 비슷하며, 채널 상관은 대체로 0.99 이상이다.
1–40 Hz 필터 후 표준편차는 채널과 파일에 따라 약 152–455 µV였다.
이는 이번 검증 도구의 보수적 100 µV 경고값을 넘는다.

11월 8일 23:47:46 GUI 기록은 `abs(value) >= 15,500 µV`인 비율이
CH1 약 0.05%, CH2 약 17.30%, CH3 약 18.92%, CH4 약 13.88%다.
이는 입력 범위 근처에서 큰 값/포화 가능성을 조사해야 할 이유다. 실제로 어느 채널에 전극이
연결됐는지, 당시 단위·접촉·설정을 확인해야 한다.

200 Hz 샘플 순서를 가정한 PSD에서 GUI 원본은 약 60.25 Hz가 매우 크고,
기존 NPZ는 약 39.75 Hz가 크다. 같은 UTC 시간으로 대략 맞춘 GUI 원본과 NPZ 사이에도
진폭·스펙트럼 차이가 있다. **필터 설정, 전송 처리 또는 다른 요인의 구분 없이 원인을 확정하지 않았다.**
특히 시간축이 틀린 데이터에서 주파수 수치를 실제 Hz로 해석하지 않는다.

공통 전극/REF 접촉, D_G, 스위치, 주변 전원 잡음, 부유 입력, 케이블, 증폭기 포화가 조사 후보다.
높은 상관만으로 젤 브리지나 reference 고장을 진단할 수 없다.
눈 뜸/감음·정답 조건을 알 수 없는 파일에서 알파 반응이나 SSVEP 정확도를 추정하지 않았다.

## 4. 로그에서 확인한 환경과 오류

`Console_2026-11-08_23-47-09.txt` 및 대응 BrainFlow 로그 기준:

- macOS 15.6.1, GUI `v6.0.0-beta.1`, 내장 BrainFlow `5.10.0`.
- Ganglion firmware 3으로 감지, BLED112 동글 경로 사용.
- 채널 설정 명령을 보낼 때 `failed to stop streaming 15` 및 `GENERAL_ERROR`.
- 이후 5초 동안 새 데이터 없음, stream stop 오류도 기록됨.

이것은 그 세션의 사실이며 현재 실행 중인 설정의 실시간 조회는 아니다.
단순히 필터나 CCA 임계값을 바꾸는 것으로 이러한 수집 오류가 해결된다고 볼 수 없다.

유사 사례로 [Mac/BLED112 느린 스트리밍 #1080](https://github.com/OpenBCI/OpenBCI_GUI/issues/1080),
[Ganglion 중단 실패 #1272](https://github.com/OpenBCI/OpenBCI_GUI/issues/1272)가 있다.
OS·버전·보드 차이가 있어 같은 원인이라는 결론은 내리지 않았다.

## 5. 다음 실험의 우선순위

1. 새 30초 GUI RAW: 샘플 수와 실제 경과시간 비교.
2. 약 83 Hz가 반복되면 배터리·보드/동글 거리·USB 경로를 하나씩 바꾸고 다시 기록.
3. GUI를 종료한 뒤 별도 BrainFlow 직접 수집으로 비교.
4. GUI가 ~200 Hz이면 LSL과 비교. LSL만 불량이면 GUI-only 알파 기록 사용.
5. 시간축이 확인된 후 REF/D_G·스위치·접촉·잡음을 정리하고 EO/EC 3쌍.
6. 단일 15 Hz OFF/ON → 주파수 변경 → 여러 자극 분류.

재검사 명령:

```bash
.venv/bin/python software/ganglion/validate_eeg.py audit \
  "$HOME/Documents/OpenBCI_GUI/Recordings" \
  software/ganglion/recordings --channels 1 2 3 4
```

감사 지표와 자동 임계값은 정상 EEG나 병적 EEG를 판독하는 도구가 아니다.
